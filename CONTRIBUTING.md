# Contributing

ImagingAgent is developed in the open. This page is the working agreement:
how branches are used, how a change travels from an idea to a release, and
what every change must satisfy. It is written so that a first-time
contributor — including me, returning after a month away — can follow it
without asking anyone.

## Branch model

Three long-lived branches, all on GitHub:

| Branch | Meaning | Who commits |
|---|---|---|
| `master` | The released state. Every commit here is something a stranger can clone and run. Release tags (`v0.1.0`, …) live here. | Only via the push block below |
| `beta` | The pre-release state: complete phases that may still receive fixes before a release. | Only via the push block below |
| `develop` | Where all work happens. | Everyone, locally |

The default branch is `master`. Both `beta` and `develop` were created from
`master` at the first commit.

Why three? Because "what I am working on", "what is finished but unreleased"
and "what is released" are three different questions, and a reader should be
able to answer each one by looking at one branch.

## Daily loop

```bash
git switch develop           # work always starts here
# ... edit, run tests, commit as often as you like ...
pytest && ruff check . && ruff format --check .
```

A change is ready when the three commands above pass locally. CI runs the
same three plus a command-line smoke test on Windows, macOS and Linux.

## End-of-phase push

Every phase (one tutorial in `docs/04-phase-tutorials/`) ends with the same
block, which fast-forwards `beta` and `master` to the tested state of
`develop`:

```bash
git switch develop
git add -A
git commit -m "<phase-specific message>"
git push origin develop develop:beta develop:master
# add --tags only when a release tag was created in this phase
git switch master
git pull --ff-only origin master
git switch develop
```

`develop:beta` means "push my local develop to the remote branch beta". The
`--ff-only` pull is a safety check: if `master` cannot be fast-forwarded,
something was pushed to it outside this flow, and the mismatch should be
understood before continuing rather than merged over.

## Release flow

1. Update `CHANGELOG.md`: move items from `[Unreleased]` under a new
   `[X.Y.Z] - YYYY-MM-DD` heading.
2. Set the same version in `pyproject.toml` and `src/imagingagent/__init__.py`.
3. Commit on `develop`, then tag: `git tag -a vX.Y.Z -m "ImagingAgent vX.Y.Z"`.
4. Run the end-of-phase push block **with** `--tags`.
5. On GitHub, create a release from the tag and paste the changelog section.

Versions follow semantic versioning. While the version starts with `0.`,
minor releases (`0.2.0`) may change interfaces; patch releases (`0.1.1`)
only fix.

## Commit messages

One line, imperative mood, prefixed by the phase when it applies:

```
phase-1: add NIfTI reader with geometry checks
docs: fix broken link in setup guide
fix: reject absolute storage keys on Windows
```

## What every change must satisfy

- **Tests pass on all three operating systems.** If a change is
  platform-specific, say so in the docs and in the test.
- **Paths use `pathlib`; storage uses the `Storage` interface.** No
  hard-coded slashes, no direct `open()` on data files outside `storage.py`.
- **Config, not constants.** A number that could reasonably change lives in
  `configs/default.yaml` and `config.py`, with the same default in both
  (`tests/test_config.py` enforces this).
- **No data in the repository.** Volumes, weights and run outputs are
  downloaded or generated by scripts; `.gitignore` keeps them out.
- **Documented.** A new file is referenced in `README.md` or a phase
  tutorial; a new term is defined in `docs/00-glossary.md`.
- **No personal data.** Only public, de-identified or synthetic images, and
  logs never contain anything that could identify a person.

## Reporting a problem

Open a GitHub issue with: the command you ran, the full output, your
operating system, and the output of `imagingagent doctor`.
